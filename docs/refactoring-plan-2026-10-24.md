# DGLab Craft 分阶段重构计划

日期：2026-10-24

## 目标与范围

在多版本之间共享反馈规则，减少遗漏移植；明确游戏状态、设备连接和发送顺序的责任，让断开、重连、退服和配置变化可验证。先保留现有优先级、租约、同步通道与续播行为，再单独讨论行为调整。

长期集成基准采用仓库默认分支 `1.20.1-Forge`；第二个试点采用 `1.21.8-Fabric`，验证跨加载器适配。当前工作目录是 `1.17.1-Fabric`，不据此决定整个项目的长期结构。旧 Forge 保留 Java 8，26.x 适配器采用对应的 Java 25。

本计划尚未实施。此次补齐版本、二维码、诊断、旧 Forge 伤害链路及明确回归缺陷，与以下架构工作分别验收。App 4.0、自定义波形编辑、基岩版和独立桥接服务另立产品需求。

## 0．先建立行为基线

从真实生产入口采集请求、状态转换和序列化报文，使用假设备传输与可控单调时钟重放。测试调用生产模块，不复制一份算式当作实现。

必须覆盖：

- 进服、退服、换世界、死亡重生、断开和重连；旧会话消息晚到；反复启停没有遗留心跳任务。
- K 键未绑定、冲突、菜单检测后进服、重新绑定；界面首次打开、缩放、返回及重复恢复默认。
- 设备上限为 0、全局比例为 0、事件倍率为 0、A/B 上限不同、活动中降低上限、非法及非有限数值。
- 波形切换为 `clear → pulse → strength`；同波形续播不清空队列；伤害高于心跳和环境；租约到期、同步/独立通道、发送失败后的状态。

验收：旧行为有可重放的输入和精确输出；故障用例能先复现，再修复。单元测试、Minecraft API 编译、游戏运行和实体设备测试分别记录，不能互相替代。

## 1．先修生命周期和强度边界

以小提交分别处理，先在两个试点分支落地，验证后移植。

1. 统一计算有效强度：设备上限、全局比例和事件禁用都必须生效。先解决请求处把 0 抬到 1 的路径，再增加发送前保护；单独按设备上限 clamp 不足以解决全局 0%。此次旧 Forge 环境倍率修复不代表所有历史发送入口已经统一。
2. 为连接持有并取消心跳任务。任务捕获所属 socket 和连接代际，关闭、失败、替换连接和停止服务都释放旧任务，不能向全局“当前连接”误发旧心跳。
3. 退出世界时，连接可用则发送停止并清理所有权；已断连则只使本地状态失效，重连保持静默。区分“本地清空”和“远端已收到归零”，不作无法验证的承诺。
4. 修正细雪重复请求与通过 `DimensionType.toString()` 判断维度的路径，使用对应版本的维度标识。每项单独建立复现和回归测试。

验收：上述边界测试通过；连续重连的活动任务数量稳定；停止后没有旧代际报文；没有把 bug 修复混入大规模文件移动。

## 2．把反馈规则收进一个深模块

建立不依赖 Minecraft、GUI 或 WebSocket 实现的 Java 8 兼容 `feedback-core`。它拥有来源优先级、A/B 所有权、租约、强度边界和波形续播决策。对外只暴露少量有业务含义的操作：提交观察/控制请求、推进时间、结束游戏会话、读取状态快照。

由核心输出不可变发送计划；协议编码器把计划转为 DG-LAB 报文。真实传输和测试用假传输消费相同计划。不要按每个字段拆出接口，也不要新增只转发调用的多层 Manager。

验收：两个试点的基线报文保持一致；切换与续播测试通过；核心测试不需要 Minecraft；Java 8 字节码检查通过。暂不引入“同帧多来源只发一次”，因为那会改变调度语义，需要独立规格和测试。

## 3．明确线程所有权和会话生命周期

游戏客户端线程拥有反馈状态和世界观察；网络回调只投递不可变消息，不能直接读写游戏对象或反馈所有权。传输层拥有 socket 与定时任务，并按连接代际丢弃过期回调。明确有界队列、关闭及背压策略。

HUD/GUI 消费只读快照。快照解决读取一致性，不能代替单一写入者；不再用零散 `volatile` 字段掩盖多线程更新。

验收：用确定的消息顺序测试连接建立、关闭、重连和晚到消息；可以证明所有状态写入发生在所属线程；关闭后队列与定时器释放。

## 4．收敛版本适配与发布元数据

先迁移 `1.20.1-Forge`，再迁移 `1.21.8-Fabric`；确认两种 API 的差异确实留在适配器后，再分批迁移其余版本。适配器只负责事件注册、读取游戏观察、按键、界面和配置桥接，不复制仲裁或协议规则。

旧 Gradle 分支消费有固定版本的核心 JAR，避免直接套用新 Loom/ForgeGradle。核心发布与游戏分支保持可追溯版本关系，不使用漂移的 SNAPSHOT。

建立一份机器可读版本清单，统一生成 README 版本表、JAR 命名、JDK、Loader、CurseForge Client 标签和发布矩阵，避免在多份工作流中手工替换。先把此次 19 个修复版本作为第一批，其他维护分支逐批接入。

验收：适配器契约测试及全部维护版本编译通过；产物中模组版本、MC/Loader 约束、字节码、依赖打包和 SHA-256 均核对；CI 能独立构建，不能把下载现有附件的上传工作流称为构建验证。

## 5．界面状态与清理

控件重建由明确的生命周期入口触发，恢复默认或连接变化时清理旧控件，不在 render 中重复调用 init。二维码首次打开仍自动生成；按 host、端口和会话缓存，连接参数改变时失效，resize 不重复生成。

按分支核查生产引用后再删除死代码。现代分支无引用的 `PulsePreviewState` 不能推导出旧 Forge 的同名实现也可删除；此次旧版本仲裁仍使用预览状态。Mixin 与资源包波形路径需先核实实际兼容用途。

验收：恢复默认、重复打开、缩放、断开重连等交互序列中控件数量稳定；首次二维码可用；波形/HUD 不倒退；删除代码有引用与兼容证据。

## 交付与回滚

每一阶段独立 PR，小步提交；行为修复、模块提取、分支迁移分别提交。每个 PR 写明故障触发、最终行为、真实验证及未覆盖项。发布先经过两个试点的客户端与设备冒烟，再扩展版本矩阵；失败时回滚该适配器或核心版本，不回滚无关分支。

建议顺序：行为基线 → 强度/会话修复 → 核心提取 → 线程收敛 → 两个试点 → 版本矩阵 → GUI 与清理。每一步以前一步验收通过为进入条件。
